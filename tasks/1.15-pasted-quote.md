# 1.15 — A pasted quote loses its `>`

## Context

Found on 2026-11-21 by task 1.12's stage 5, which recorded it as not its own;
picked up on 2026-11-28, asked for by the user, as the first fix of stage 5 of
the rewrite. A blockquote pasted or dropped anywhere that is not itself inside
a quote is drawn as a quote and written without one: every line of it goes into
the file with no `>`, so the next open shows plain paragraphs.

Measured that day with `modelInsertBlocks` on a parsed fragment, before any
change:

- `x`, `> A`, `y` pasted into `one two` writes `onex`, `A`, `y two`.
- The same into a bullet writes the quote's lines flush left, so they also
  leave the list.
- A heading, a list or a table inside the pasted quote loses its `>` the same
  way; a fence and a bare `>` line keep theirs, so a quote holding both comes
  back as a heading and then a quote.
- A quote nested in a pasted quote loses both levels.
- Pasted into a quote, the pasted quote's lines carry the landing quote's `>`
  and not their own, so it stops being nested.

The cause is one line. `modelAdoptBlocks` gives every pasted block the quote
chain of the block it lands beside, in place of the chain the block recorded
in the document it was parsed from. For a block that was in no quote that is
right. For one inside a pasted quote, its own chain is the only record of that
quote's `>`: a quote is a container and writes nothing itself.

### The plan

1. **Compose, not replace.** A pasted block that recorded a chain keeps it,
   moved to where it lands: each line's prefix is the landing quote's prefix,
   then the block's own prefix with its indent moved to the landing column.
   A block inside a pasted quote keeps the `leadingAffix` it recorded, since
   its place inside the pasted block has not changed, and an item inside a
   pasted quote keeps its marker unmoved, since the chain in front of it now
   carries the column.
2. **The landing column is the emitter's.** The column pasted items and
   fences move by is taken from `modelItemAffix`, not `modelItemAncestor`, so
   a landing block in a quote inside an item adds no indent after the `>`
   that already carries it. The composed chain needs this to be right.
3. **Blank lines inside a pasted container, landing in a quote.** A loose
   list's blank separators are written with the landing quote's `>`. Without
   it a pasted item holding a quote, landing in a quote, would still split
   the landing quote; the same fix covers a loose list with no quote in it.
4. **Checks.** `model` cases for each shape measured above, at the top level,
   in a quote and in a bullet; a sweep that pastes every quote-bearing
   top-level block of `tests/fixtures/torture.md` at all three and compares
   bytes; a Playwright case that pastes a quote as HTML and reads the
   markdown a save would write.
5. **Records.** CHANGELOG.md, this file, `tests/browser/copy-gap.spec.mjs`'s
   comment that names this bug.

- [x] The Playwright case passes in Chromium, Firefox and WebKit
- [ ] Erez copies a quote out of a web page and out of Mandy with a real
  clipboard, pastes each outside a quote, saves and reopens, and reports the
  quote kept

**Found on the way and not this task's**, each measured the same day:

- Pasting several blocks into a quote that opens a list item (`- > one two`)
  writes them outside the list. The landing block's chain is `""` on its
  first line, its `>` being in its `leadingAffix`.
- A quote indented four columns or more under a nested item (`    > q` under
  `  - b`) records no chain, so editing its second line writes it flush left.
  A parse fault, with no paste in it.
- A heading pasted as a middle block into a bullet is written flush left,
  outside the list, ATX or setext: a heading's `open` is never moved to the
  landing column. It is why the sweep in the plan pastes at the top level and
  into a quote, and not into a bullet.
- A landing quote written `>` with no space after it (`>one two`): a pasted
  item holding a quote or a fence is written `>  > q`, where the `>` takes one
  of the item's two indent columns, so the quote or fence reopens beside the
  list and not inside the item. Wrong before this task too, in other bytes.

## Decisions

### 2026-11-28 · A pasted quote's chain is composed, not parsed again

**Decision** — `modelAdoptBlocks` keeps the chain a block inside a pasted quote
recorded and puts the landing quote's prefix and the landing column in front
of each line of it.
**Rejected** — Writing the pasted quote as text at its landing place and
parsing it again, the way Format → Blockquote wraps and unwraps.
**Why** — The toggle parses a top-level block it already holds; a paste would
have to rebuild the landing block's containers as text to parse inside them,
before the split and the merges the insertion still has to make. The affixes a
pasted block recorded are right for its own bytes and only move, which the
sweep over torture.md checks byte for byte.

### 2026-11-28 · The landing column is the emitter's

**Decision** — When the landing block's chain holds a `>`, the column pasted
items, fences and chains move by is read through `modelItemAffix`, which stops
at a quote. When it holds none, it is the nearest item's, as before.
**Rejected** — `modelItemAncestor` everywhere, as before, which finds an item
above a quote too. `modelItemAffix` everywhere, which the first draft did.
**Why** — A landing block in a quote inside an item has the item's indent in
its chain already. Adding it again wrote `  >   - x` for a pasted list and
would have written `  >   > q` for a pasted quote. This also moves what Format
→ Code writes for a code block made in such a quote, to `  > ` and the fence.
The two landings under "Found on the way" whose chain was never recorded have
nothing carrying the indent, and the reader found that `modelItemAffix` alone
moved a list or fence pasted there, and a code block made there, out of the
list; they are wrong either way and keep the bytes they had.

### 2026-11-28 · Blank lines inside a pasted container take the landing quote

**Decision** — A blank line between two blocks of a pasted container is written
as the landing quote's bare `>`, and a `>` line there is moved as a chain is.
**Rejected** — Leaving the separators as parsed and fixing only the chain.
**Why** — A pasted item holding a quote, landing in a quote, would still end
the landing quote at its blank line, so the chain fix alone leaves its own
case broken. The same line fixes a loose list pasted into a quote, which had
the fault with no pasted quote in it.

### 2026-11-28 · A bare `>` line is written without a space after it

**Decision** — On adoption a line that is nothing but a quote chain loses its
trailing whitespace, in a gap block's bytes and in a separator.
**Rejected** — Keeping the pasted bytes, which is what a fence gets.
**Why** — Turndown writes every blank line of a quote as `> `. Before this
task those lines were the only ones of a pasted quote to keep their `>`; with
the quote kept they would put trailing whitespace on each. The emitter already
writes an empty quoted line as `>`, and D3 leaves invisible whitespace out of
fidelity.

### 2026-11-28 · A lazy line is not indented under a bullet

**Decision** — A line of a pasted quote that recorded no `>` gets the landing
quote's prefix and nothing else, so under a bullet it is written flush left.
**Rejected** — Giving it the item's indent, which is what its bytes would be
if the quote had been typed there.
**Why** — The emitter takes no item affix inside a quote, so an indent on that
line would have to live in the chain as a prefix with no `>` in it, which
`modelBlankSeparator` and the gap joiner both read as a line outside the quote.
Flush left it is still a lazy continuation and parses to the same quote.

## Review · 2026-11-28

### Format → Code and a pasted list or fence leave the list when the landing quote recorded no chain

**Found** — `front/model.js`, `modelAdoptBlocks`, `const item =
modelItemAffix(like)`. In a quote four or more columns in and in a quote
opening an item the landing chain holds no `>`, so the column became 0 and a
list or fence pasted there, or a code block made there, was written flush
left, outside the list it had stayed inside before.

**Done when**

- [x] A list or a fence pasted into `    > one two` under `  - b` → written at four columns, inside item b, as before the change
- [x] Format → Code on that paragraph → the fence at four columns, as before
- [x] Format → Code on `- > one two` → the bytes it wrote before
- [x] A list pasted into `- a\n\n  > one two` → still `  > - x`, with no indent after the `>`
- [x] Format → Code in `- a\n\n  > one two` → still `  > ` and the fence
- [x] Table of contents and Insert → Table at every landing → bytes unchanged

**Not asked** — fixing the four-column parse fault or the quote-opening-an-item
fault; a second way of reading the landing column.

### A pasted item holding a quote or a fence leaves its item when the landing quote is written `>` with no space

**Found** — `front/model.js`, `modelAdoptBlocks`, `moved` and the fence branch:
the landing prefix is the chain as written, so into `>one two` a pasted
`- i` holding a quote is written `>  > q` and reopens with the quote beside
the list. Wrong before the change too.

**Done when**

- [x] `- i\n\n  > q` pasted into `>one two` → listed under "Found on the way" as measured and not fixed
- [x] `- x` holding a fence pasted into `>one two` → listed likewise
- [x] The same two pastes into `> one two` → `> - i\n>\n>   > q`, unchanged
- [x] `> A` pasted into `>one two` → still a nested quote

**Not asked** — rewriting the landing quote's own `>` spelling on lines the
paste did not write.
