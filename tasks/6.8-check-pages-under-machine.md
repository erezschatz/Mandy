# 6.8 — The check pages run under a machine

## Context

Raised on the `rewrite` branch as docs/TODO.md 6.8 on 2026-10-13 and carried
here at the 2026-10-26 merge of `main`, since docs/TODO.md was retired on
`main` on 2026-10-19 while the branch was still writing to it. The item as it
stood, measurements and status included, since the branch recorded both in it:

*(survives 3.1)* The check pages run under a machine.
[tests/browser/](../tests/browser/) is a Playwright harness — the one
dependency with a browser engine in it this project has agreed to, on
2026-10-13, reversing ROADMAP.md's "a full frontend test harness is not
being planned" — that drives the self-running check pages through
Chromium, Firefox and WebKit and judges the report each one POSTs. Stage
one landed the same day: `browser-check`, `list-indent-check` and
`list-empty-item-check`, one test each per engine, `npm run test:browser`.
The Tests section of [CLAUDE.md](../CLAUDE.md) says what it measures and
what it does not. **Done, untested in Firefox** — Chromium and WebKit
since 2026-10-21, below. Originally: the harness was
driven in Chromium only, from a machine with no CDN, so `browser-check`
came back with no problems and the two list pages with the harness's own
*measured nothing*, which is the right answer there. The first run with
all three engines and the CDN is the one that moves this to *done and
tested*.

What follows, in order, each written up here as it lands:

1.  **The trusted-keystroke half.** The list pages press keys with
    `new KeyboardEvent`, which is untrusted, so whether the native split is
    suppressed was measured by hand with a real keyboard (CLAUDE.md, the
    2026-09-13 run). Playwright's keyboard is trusted. A spec that drives
    the running app with real keystrokes answers that half, and is the
    shape every input-layer measurement after it takes. *Not started*
    as a spec — but whether it can work at all was measured first, below.

    **Measured 2026-10-18: Playwright's keyboard yields real editing
    commands in Chromium and WebKit, and Firefox did not launch.**
    Playwright 1.58.2 on macOS 27.0.1 (26A434), driving a bare
    `contenteditable` of two `<p>` blocks with `page.keyboard.press` and
    `page.keyboard.type`, no app loaded. Every `beforeinput` that fired
    was `isTrusted` and `cancelable`, and the engine then performed the
    edit — the opposite of the 2026-09-20 Blink measurement CLAUDE.md
    quotes, which used a different automation path:

    | Keystroke | Chromium 145.0.7632.6 (v1208) | WebKit 26.0 (v2248) |
    | --- | --- | --- |
    | Backspace at start of block 2 | `deleteContentBackward`; ranges span both blocks | `deleteContentBackward`; ranges span both blocks |
    | Enter mid-word | `insertParagraph` | `insertParagraph` |
    | Shift+Enter mid-word | `insertLineBreak`, a `<br>` | **`insertParagraph`**, a split |
    | Typing `abc` | three `insertText`, one per letter | three `insertText`, one per letter |
    | Alt+Backspace at end of line | `deleteWordBackward` | `deleteWordBackward` |
    | Tab | no `beforeinput`; focus left the editor | no `beforeinput`; focus left the editor |

    "Span both blocks" means the one target range ran from the end of the
    first block's text node to offset 0 of the second `<p>`, in both. The
    WebKit Shift+Enter is the row not to build on: whether real Safari
    does the same, or this is Playwright's own key-to-command mapping
    rather than the engine, was not measured, and a spec that asserted it
    would be asserting one or the other on a guess. **Firefox 146.0.1 (v1509) is unmeasured**:
    its launch timed out on this machine with
    `sandbox_extension_issue_file_to_process … Operation not permitted`
    for `plugin-container.app`. `MOZ_DISABLE_CONTENT_SANDBOX=1` clears
    that error and it then fails on `RenderCompositorSWGL failed mapping
    default framebuffer`; launched from the user's own Terminal, outside
    any agent sandbox, it simply hangs. Most likely Playwright 1.58's
    Firefox build does not run on this macOS, and the likely fix is a
    bump to Playwright's current release, 1.64.1, which wants the user's
    go-ahead first and has not been made. Until then the harness's own
    Firefox run above cannot happen on this machine either. Separately,
    `npm run engines` (`playwright install`) hangs in its own unzip under
    Node 26.12 — one run sat for 23 hours after a ten-second download —
    so the engines in the cache were unpacked by hand with `ditto` and
    marked `INSTALLATION_COMPLETE`. The probe was a
    throwaway spec and was deleted rather than kept; `input-check.html`
    was not driven, and is the next thing to try now that the first pass
    came back positive.

    **The bump was made on 2026-10-21, and it did not fix Firefox.**
    Playwright 1.64.1 brings Chromium 156.0.8078.4 (v1248), Firefox 157.0
    (v1555) and WebKit 27.2 (v2370). Its own installer worked first time,
    all three in under four minutes, so the unzip hang is 1.58's and
    nothing is unpacked by hand any more. Re-run on the same probe, the
    Chromium and WebKit columns above came back **unchanged in every
    row**, WebKit's Shift+Enter `insertParagraph` included. Firefox 157
    fails differently rather than not at all: it exits within 100ms of
    launch with `Could not find profile folder.`, although Playwright has
    just created the folder it names. The same both inside and outside
    the agent's command sandbox, and with the profile under
    `/var/folders`, the scratchpad or `~/.cache`. So **Firefox is still
    unmeasured on this machine**, now with a fast, clear failure where
    1.58's hung, and the next question is Firefox's, not the harness's.

    Found on the way, and **not caused by the bump**: the two list pages
    fail as *measured nothing* in Chromium and WebKit on this machine, under
    1.58.2 and 1.64.1 alike, inside the sandbox and out. Out of the
    sandbox the CDN loads; what fails is the app frame's own same-origin
    scripts (`app.js`, `undo.js`, `tabs.js` and the rest), each
    `ERR_ABORTED` about 400ms in, which reads as the page being torn
    down while its frame is still loading rather than as anything
    missing. `browser-check` passes in both.

    **Diagnosed and fixed the same day: the pages had always measured, and
    the harness was reading their own navigation as lost resources.** A
    request timeline per frame, on the worktree's own server rather than
    whatever held :9130, showed two sources of aborts and nothing else.
    The frame was navigated twice: the markup's `<iframe src="/">` began
    booting the app, and `fresh()` re-pointed it at `/?fresh=…` some 20ms
    later, after clearing the service worker, which cancelled every script
    the first load had in flight — that is the run the report above saw.
    And once the report was written, the page removed its frame on
    purpose, so a debounced autosave cannot land after it restores the
    tester's keys, which cancelled what the app still had out: the
    `/api/home` its own `visibilitychange` wake fires on the way out, a
    web font, sometimes `welcome.md`. The cases themselves run
    synchronously in one task against the second load and had come back
    `check: 0 problems` all along. A late `welcome.md` cannot land between
    two of them for the same reason. Two changes: both pages ship the
    frame with no `src`, so `fresh()` is its only navigation; and the spec
    drops a failure only when it is an abort (`net::ERR_ABORTED`,
    WebKit's `cancelled`) from a frame that has since been detached, which
    is the teardown and nothing else. Checked against a control: with
    `cdn.jsdelivr.net` blocked by `page.route`, both list pages still fail
    in both engines with `ERR_INTERNET_DISCONNECTED`, so the guard the
    filter sits in front of still does its job.

    **Run 2026-10-21, Playwright 1.64.1, Chromium 156.0.8078.4 and WebKit
    27.2 on macOS 27.0.1: all three pages, both engines, 0 problems** —
    `list-indent-check` and `list-empty-item-check` for the first time
    under this harness. Firefox was not run, for the reason above.

    **Stays by hand however this goes**: real IME composition, macOS
    press-and-hold accents (both are system input methods Playwright's
    keyboard does not go through), and real Safari as distinct from
    Playwright's WebKit — which the Shift+Enter row is the first evidence
    is a real distinction rather than a formality.

    **The first spec is `tests/fixtures/format-check.md`'s "Typing an
    equation" section** — planned 2026-10-21, because it is slice 7's step
    10 and the hand run every later step is waiting behind.
    `equation-typing.spec.mjs` loads `/?core=model` in a fresh profile,
    turns on `modelVerifySetEnabled(true)`, and loads the fixture itself,
    read off disk and handed to `loadDocumentMarkdown`, so it starts from
    the same document a hand run does. There is no file dialog, which is
    what File → Open would cost. Each of the section's numbered steps is one
    test, typed with Playwright's keyboard and mouse into a new paragraph at
    the end, and judged three ways: what the paragraph shows (an equation
    exists or does not), where the next typed letters land, and what
    `htmlToMarkdown(editor.innerHTML)` would write, which is the save path
    step 8 checks by hand. Every test fails on a `[model] render diverged`
    warning or any console error, as the protocol does. Step 3's click
    after a one-glyph equation, which is the `233af6a` bug, gets a test of
    its own.

    It replaces the hand run in Chromium and WebKit, not in Firefox. Two
    things stay by hand even there: whether the conversion toast looks
    right, since the test checks only that it says what it should, and
    whether the display equation in step 6 is *centred*, which is layout a
    person judges.

    **Done and tested, 2026-10-21, in Chromium 156.0.8078.4 and WebKit
    27.2** (Playwright 1.64.1, macOS 27.0.1). Ten tests, the protocol's
    eight steps plus two for the click after a one-glyph equation, and all
    but one pass in both engines. The centring turned out to be measurable
    after all, as the distance between the equation's centre and the
    line's, so only the toast's look stays by hand. The run also showed
    what the hand protocol had been taking on trust. **WebKit puts a click
    anywhere after an equation that ends its line in front of it.** The
    caret lands at the end of the text before the equation, so neither
    caret handler sees it. It was fixed the same day as step 10's second
    round of fixes (docs/REWRITE.md), and the test now passes in both
    engines.
    The other surprises were the spec's, not the app's. A press within a
    couple of pixels of an equation lands on the equation, so the drag
    starts twenty pixels out, as a hand's does. A letter typed in the same
    instant as a click beats the selection update that moves the caret, so
    the spec waits for it, as `233af6a`'s entry said a machine must. And
    the fixture quotes the very text the steps type, so the save checks
    read the document's last lines rather than searching it. Each check
    that guards a fix was confirmed to fail without it: with `233af6a`
    switched off in the page, the Q lands in front of the equation. On the
    first cold run, step 2 once logged a console error that never came
    back; if it does, the run says so, since every test fails on one.

    **The second is `format-marks.spec.mjs`**, 2026-10-24, for slice 7's
    step 3: bold, italic and strikethrough through the format bar and the
    Format menu, judged by the markdown the model holds rather than the
    save path, which is still the old core's. Done and tested in Chromium
    and WebKit on its first day. It learnt one thing about the platform:
    on macOS, WebKit takes Home and End to scroll the page and leaves the
    caret where it is, so the spec moves along a line with Cmd+Left and
    Cmd+Right there, as a Mac user does.
2.  **Open, edit, save.** The `break-test.md` recipe as a spec: load the
    app, open the fixture through the file API, make the edit, Save As to
    a scratch name, diff against the fixture, delete the scratch — the
    recipe CLAUDE.md gives for a hand run, so "never save over it" is the
    spec's own rule. Run twice, `?core=legacy` and `?core=model`, and the
    two outputs compared: that parity is the gate for the stage 4 merge,
    which is irreversible. *Not started.*
3.  **`caret-guard-check` and `input-check`**, the pages that need a caret
    and a keystroke, driven the same way. *Not started.*

Stays by hand: real Safari, periodically, for anything with a Safari
version on it; `tab-shortcut-check`'s "did the browser's own tab switch",
which is browser chrome no page-level automation can see; and
`paste-check` outside Chromium until a driven keystroke is confirmed to
reach the engine's own plain-text paste binding.

6.6's "the check pages are run by hand from a dev server" now reads "by
hand or by this": a `MANDY_DEV` gate on `/tests/:name` and `/report` has
to be set by the harness's server command as well.
