# 4.14 — Reload all from disk

## Context

Asked by Erez on 2026-11-24. He reads files that are generated over and over,
so he reloads a lot: five tabs open, three of them needing a reload. Wanted: a
File menu action that reloads every open tab from disk. Tabs must not reach
into each other, so the action has to be the existing *Reload from disk* run
once for each tab, with no new code that works across tabs.

The plan, in one stage:

- **File → Reload all from disk**, app-only, right below *Reload from disk*. It
  is disabled with the other file items when the server is unavailable.
- **`reloadAllTabs()` in `tabs.js`** goes through the bar in order. For each tab
  with a file it calls `switchToTab(id)` and then `reloadFile()`, and when it is
  done it switches back to the tab it started on. Those are the two calls a user
  would make by hand: click the tab, then File → Reload from disk. It reads
  nothing from another tab's state and writes none. Which tabs have a file is
  read through `tabDescriptor`, the same function the bar uses.
- **A tab with no file is skipped**, so you do not get a "No file is open to
  reload." notice for each one.
- **An edited tab gets Reload's own question, on screen and by name**
  (`confirmDiscard`, through `reloadFile`). Cancel keeps that document as it is
  and the run moves on to the next tab.
- **A switch that is refused ends the run.** That only happens when a file
  operation is in flight, and then the screen is not on the tab the next reload
  would act on.
- With no tab list (a session whose migration failed), it is a single Reload.

Tests: the `tabs` suite (every tab with a file reloaded from the fake disk, the
skip, the return to the starting tab, an edited tab asked about by name, Cancel
keeping that tab), and the `toolbar` suite for the new item having a handler in
the app bundle.

### Stage 2 — a cover while it runs (planned 2026-11-24)

Stage 1 visibly switches through every tab. With five tabs that looks odd, and
with ten it would look like the computer had gone wrong. Erez asked for a cover
over the app while the run works, which comes down when it is done. He chose
option 1 for edited tabs: lift the cover for the question, which is how most
apps do it.

- **`busy(message)` in `notify.js`**, since that is the only place `front/`
  talks to the user outside the document. It puts a full-window cover up, with a
  spinner and the message, above the file dialog and below `ask()`'s dialogs and
  the toasts, so the "Reloaded …" toasts still show over it. It returns
  `{ update(message), done() }`. `done()` removes the cover at once, with no
  exit fade, so a question raised right after is never under a fading cover.
  `done()` is safe to call twice.
- **`reloadAllTabs()` puts it up before the first switch**, so the first paint
  already has the cover, and updates it to "Reloading *n* of *m*…". Nothing
  about the run underneath changes: still one switch and one `reloadFile()` per
  tab.
- **An edited tab lifts the cover.** After the switch, if `documentIsDirty()`
  (the same check `confirmDiscard` makes) the cover comes down, so you see the
  tab and its question, and goes back up after you answer, if there are tabs
  left.
- **It always comes down**: the run is wrapped in `try`/`finally`. A cover left
  up would make the app look dead until a page reload.
- **Not shown when nothing is reloaded**: with no tab holding a file, no cover
  goes up.

Tests: the `notify` suite for `busy` (up, the message, update, done removes it,
done twice), and the `tabs` suite for the cover being up during each reload,
down during an edited tab's question, down at the end, and down when a reload
throws.

## Decisions

### 2026-11-24 · Reload all is Reload, once per tab, on screen

**Decision** — `reloadAllTabs()` switches to each tab with a file and calls the
existing `reloadFile()`, then switches back to the tab it started on. Cancel on
an edited tab keeps that tab and the run goes on.
**Rejected** — reading each background tab's file straight into its parked
bundle or storage without switching to it, and stopping the whole run on the
first Cancel.
**Why** — tabs do not act on each other's state. `reloadFile` and its guard only
ever ask about the document on screen, so switching first is the only way to
reuse them unchanged. This is the same reason `requestCloseTab` switches before
it asks. Cancel in that dialog means "keep this document", and when one tab of
five is edited, keeping it is no reason to leave the other four stale.

### 2026-11-24 · An edited tab lifts the cover for its question

**Decision** — Reload all runs under an opaque `busy()` cover, and an edited tab
takes the cover down for Reload's question and puts it back up after the
answer.
**Rejected** — asking every edited tab's question up front, in a pass over the
tabs before the cover goes up; and a see-through cover over the switching.
**Why** — the question is about a document you have to be able to see, and
lifting the cover is how most apps handle it (Erez's call). Asking up front
would mean a second pass over the tabs before the real one. A see-through cover
would still show the switching it is there to hide.

## What was done

Done and tested. File → Reload all from disk (`reload-all-files`, app-only,
disabled without the server) runs `reloadAllTabs()` in `tabs.js`, as planned
above. The `tabs` suite covers the reloads, the skip, the return to the starting
tab, the question about an edited tab and its Cancel, and a refused switch; the
`toolbar` suite covers the item. Not yet checked by hand in a browser.

The reader found that a switch refused partway through returned without trying
to go back to the starting tab. The loop now breaks there instead, so the
switch back is still tried, and the same lock may refuse it too. It also found
that the skip and a lock taken partway through had no check that could fail.
The harness now records notices, and two cases were added: a background tab
with no file is never switched to, and a lock taken during the first tab's
question stops the run there. Each was confirmed by removing the line it covers
and watching the suite fail. One case is stated rather than changed: when the
starting tab has a file and is first in the bar, it is reloaded even under the
lock, as a plain Reload would be, because `switchToTab` to the tab on screen
returns without asking the lock.

## What was done

Stage 2, done and tested. `busy()` in `notify.js`, with its styles in
`app.css`, and `reloadAllTabs()` now runs under it, as planned in the Context's
stage 2. The cover comes down for an edited tab's question and goes back up
after it, and a `finally` takes it down on a throw. The `notify` suite covers
`busy`. The `tabs` suite covers the cover being down during the question and up
for every reload after it, down at the end, never raised with no file to
reload, and down after a throw. The lift and the `finally` were each removed
once to confirm their checks fail. Not yet checked by hand in a browser: how
the cover looks in both themes, and whether any of the switching shows through
before it.

The cover goes back up at the start of the next tab rather than right after the
answer, so the edited tab's own reload and its toast happen in view. When the
last tab with a file is the edited one, the switch back to the starting tab is
in view too. The list of tabs to reload is now worked out once, before the
loop, rather than as each tab is reached.

The reader found that the cover stopped the mouse and not the keyboard, as
recorded in the review below. `busy()` now swallows every keydown at the window,
in the capture phase, while it is up, and gives the keyboard back in `done()`.
The `notify` suite checks both, and removing the swallow fails the check. The
boxes below are ticked on the code path: every case is a keydown that never
reaches a listener behind the cover, and `done()` runs before any question is
asked. None of them has been tried by hand.

## Review · 2026-11-24

### The cover does not stop the keyboard reaching the hidden app

**Found** — `front/notify.js` `busy()` only put a div on top. The
document-level keydown listeners in `file-api.js`, `app.js`, `undo.js` and
`toolbar.js`, plus Tab and typing, still acted on the hidden app while each
read was in flight. Ctrl+O opened the file dialog under the cover and made the
next switch refuse. Ctrl+S could raise `confirmOverwrite` about a tab nobody
could see. Typing and Ctrl+Z went into the hidden editor. Tab walked focus
through the hidden toolbar.

**Done when**

- [x] Cover up, Ctrl+O pressed → no file dialog opens; the run goes on and reloads every remaining tab.
- [x] Cover up, Ctrl+S or Ctrl+Shift+S pressed → nothing is saved and no question appears.
- [x] Cover up, keys typed or Ctrl+Z pressed → the hidden document is unchanged and the reload result is exactly the file on disk.
- [x] Cover up, Tab or Shift+Tab pressed → focus does not reach the toolbar, tab bar, menus or editor behind the cover.
- [x] Cover lifted for an edited tab's question → the dialog's Tab cycling, Escape-as-Cancel and Enter work as they do today, and so does a Save that leads into `confirmOverwrite`.
- [x] Cover taken down at the end, by a refused switch or by a throw → every shortcut, typing and Tab work as before, and focus is where it was before the run, or in the editor.
- [x] No Reload all in progress → Ctrl+O, Ctrl+S, typing and Tab behave exactly as now.

**Not asked** — no Cancel or Stop button for the run. No new lock or counter in `file-api.js`. No change to `ask()`, `confirmDiscard`, `reloadFile` or the `switchToTab` gate. No notice for a run that stops on a refused switch, beyond what the cases above need.
