# 1.16 — A heading pasted into a list item is written outside the list

## Context

Found on 2026-11-28 by task 1.15, which measured it and left it; picked up the
same day, asked for by the user. A heading pasted or dropped as a whole block
into a list item is drawn inside the item and written flush left, so the file
ends the list at the heading and the next open shows it outside.

Measured that day with `modelInsertBlocks`, before any change:

- `A`, `# h`, `B` pasted into `- one two` writes `- oneA`, a blank line, `# h`
  at column 0, a blank line, `  B two`.
- The setext spelling, `h` over `===`, is written at column 0 on both lines.
- A heading inside a pasted item (`- i` holding `  #### h`) pasted into a
  bullet keeps the two columns it had and gains none, so it leaves the item it
  was pasted in.
- Into an item inside a quote (`> - one two`) it is written `> # h`, in the
  quote and outside the list.

The cause: a heading takes no item affix from the emitter. Its `open` was read
off its own line from column 0 and already holds whatever indent it sat under,
and a setext heading's `underline` likewise. `modelAdoptBlocks` moves an item's
marker, a fence's bytes and, since task 1.15, a quote's chain to the landing
column, and leaves a heading's shape as it was parsed.

### The plan

1. `modelAdoptBlocks` moves a pasted heading's `open`, and its `underline`
   when it has one, by the landing column, the way it moves an item's marker.
   Not for a heading inside a pasted quote: its shape was read off the line
   behind the chain, and task 1.15 puts the column in the chain.
2. `model` cases: ATX and setext into a bullet, into a nested bullet, into an
   item inside a quote, a heading inside a pasted item, one with a closing
   run, and the landings that must not move: the top level, a quote, and a
   heading inside a pasted quote under a bullet. Then one case that types
   into the pasted heading.
3. A Playwright case pasting a heading as HTML into a list item and reading
   the markdown a save writes.
4. Records: CHANGELOG.md, this file, task 1.15's sweep, which can take the
   bullet landing if this is what kept it out.

- [x] The Playwright case passes in Chromium, Firefox and WebKit

## Decisions

### 2026-11-28 · A pasted heading's shape is moved, and the emitter is left alone

**Decision** — `modelAdoptBlocks` adds the landing column to a pasted heading's
`open` and `underline`.
**Rejected** — Having `modelEmitLeaf` give a heading its item's indent like any
other leaf, with `open` recorded without it.
**Why** — A parsed heading's `open` holds its indent already, and stage 1
pinned that the shape plus the chain is the heading's own source. Changing the
emitter would change what every heading in an item is written from, to fix the
one path that puts a heading somewhere new.

### 2026-11-28 · A two-line setext heading's second line is written flush left

**Decision** — Only `open` and `underline` move, so the second content line of
a pasted setext heading of two lines carries no indent.
**Rejected** — Indenting every content line, which needs the emitter to know a
heading's continuation indent.
**Why** — The shape has no field for it: a setext heading parsed inside an item
with two indented lines records no shape at all and is refused on edit, an
older limit. Flush left the line is a lazy continuation, and the file reopens
with one heading inside the item.

### 2026-11-28 · A heading under a pasted item moves as far as that item's content did

**Decision** — The columns added to a heading are the landing column at the
top of what was pasted, and under a pasted item the difference between the
column its marker ended at before and after the move. They are added as spaces
after whatever indent the heading had.
**Rejected** — Moving every heading by the landing column through
`modelShiftIndent`, which the first draft did.
**Why** — A tab-marked item pasted two columns in still starts its content at
column 4, so its heading must not move, and `modelShiftIndent` rounds a move
to whole tabs when the indent holds one; the reader found the draft turned
such a heading into a code block. Spaces after the indent add exactly the
columns asked for, where a tab after them would swallow some.

### A heading pasted where the quote opens the item's first line still leaves the quote

**Found** — `front/model.js`, `modelAdoptBlocks`: into `- > one two` the
landing chain is `""`, so nothing pasted is written behind a `>`. Task 1.15
lists the landing as measured and not fixed. The heading there is now written
`  # h` where it was `# h`: in the item and outside the quote, where it was
outside both.

**Done when**

- [x] `A`, `# h`, `B` pasted into `- > one two`, `- > - one two`, and an item behind `>` with no space → named in the record below as not covered
- [x] `> - one two`, `> > - one two`, `   > - one two`, and `- x` holding `  > - one two` → the heading reopens inside the item

**Not asked** — it need not land in 1.16; the record should only stop short of
implying every quote-and-item landing is covered.

### A pasted item that opens with a heading cannot be saved

**Found** — older than this change: `- # h`, `- h` over `  ===` and `- > # h`
pasted anywhere, and a paste into a heading that opens an item, make the
emitter throw `edited heading with no recorded shape`, since a heading
opening an item records no shape and adoption clears its source.

**Done when**

- [x] `- # h` and `- h` over `  ===` pasted as a whole block → named in the record below as an older fault, not fixed
- [x] a heading as a pasted item's second child → bytes as the suite's case has them

**Not asked** — not part of 1.16; a task of its own if wanted.
