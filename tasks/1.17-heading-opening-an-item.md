# 1.17 — A heading that opens a list item cannot be saved once edited

## Context

Found on 2026-11-28 by the reader of task 1.16, as a pasted `- # h` making the
save throw; picked up the same day, asked for by the user. Measured before any
change, it is wider than a paste: **typing one letter into a heading that opens
a list item** makes the emitter throw `edited heading with no recorded shape`,
so Save reports the document cannot be written and the autosave stops at the
last version that could. Undoing the edit is the only way out.

The headings that record no shape, each measured by parsing it and typing into
it:

- one that opens a list item, in any spelling: `- # h`, `1. ## h ##`, `- #`,
  `-\t# h`, `- h` over `  ===`, the second item of a list, an indented list;
- one that opens an item which opens an item, `- - # h`;
- one that opens an item inside a quote, `> - # h`;
- one indented four columns or more under a nested item, `    # h` under
  `  - b`, which opens nothing;
- a setext heading of two lines indented under an item, `  h1`, `  h2`, `  ---`;
- one that opens a quote which opens an item, `- > # h`.

The cause is in `modelHeadingShape`. It reads a heading's opening off its first
line and expects up to three spaces and then the hashes, or for the setext
spelling the text itself. A heading that opens an item has the item's marker
in front of it on that line, a deeper one has more than three spaces, and a
two-line setext heading under an item has an indent on its second line that
the parser's content does not. Each records `null`, and the emitter refuses a
heading with no shape.

Mandy offers no way to make a heading in a list item (task 1.1.5), but it
opens files that hold them and pastes them, and both reach this.

### The plan

First written 2026-11-28 as a narrower change: read the shape behind the
item's marker, mark it, and have the emitter write that marker from the item.
The reader found it turned loud failures into wrong bytes (the Review section
below), and the plan was rewritten the same day, before anything was
committed. This is the plan that was built.

1. **A heading directly inside a list item is read with the item's prefix
   taken off**, in `modelItemHeadingShape`, called by the tiler once an item's
   children are known: the marker off a line that opens the item, the
   continuation indent off every other. `modelHeadingShape` itself is
   unchanged and reads what is left.
2. **The emitter writes a heading positionally, as it writes a paragraph**:
   the item's marker when the heading opens the item, its continuation indent
   otherwise, and the indent on every later line, a setext underline included.
   So whatever moves or re-marks the item moves the heading: a list switch, an
   indent, an outdent, an unwrap, Enter.
3. **A heading whose lines do not carry the item's prefix keeps the shape it
   had and is marked `absolute`**: its `open` holds its indent and the item
   adds nothing, which is how every heading in an item was written before.
4. **Adoption** (tasks 1.15 and 1.16) has nothing to do for a positional
   heading that lands in an item. It still puts the columns into an `absolute`
   one, and into a heading landing where the emitter will not give it the
   item. A pasted item's continuation indent, the items under it, a fence's
   bytes and a quote's chain now move as far as that item's content did, where
   they moved by the landing column: the same for spaces, and right for a
   tab-marked item, whose content a two-column landing does not move. Only at
   a landing with no quote chain; behind a `>` they move by the landing
   column, as before.
5. **Two emitter spellings** the reader found a heading in an item can now
   reach, wrong at the margin before this: content typed into `# #` ran into
   the closing run, and a setext heading emptied by Enter at its start wrote
   its underline as text.
6. **Checks.** `model`: every shape listed above emitted from its tree back to
   its own bytes, with the setext shapes the first draft stopped recording;
   each operation that moves an item checked against a parse of what it
   wrote; the pasted cases; the two spellings. Playwright: open a file with
   `- # Title`, type into the heading, press Enter, read what a save writes.
7. **Records.** CHANGELOG.md, this file, CLAUDE.md's heading paragraph.

Not in this task, and still refused with a throw, as before it:

- `- > # h`, a heading opening a quote that opens an item. The quote stands
  between the heading and the item, and the emitter gives no item affix across
  a quote.
- `- - # h`, a heading opening an item that opens an item. The inner item's
  marker is not the first thing on its line; a paragraph there keeps the other
  marker in a leading affix that goes stale when the inner list changes, and a
  heading is not given the same fault.
- A heading opening its item whose later line is lazy, `- h1`, `h2`, `  ===`:
  the line is short of the item's indent, and it had no shape to keep.

Two things reach a refused shape that did not before, both found by the second
reader. Format → Blockquote over `- # h` now writes `- > # h`, where the
toggle itself threw; the next letter typed into it is refused. And a pasted
item that opens with a heading, landing in a quote that opens an item
(`- > one two`), is now written outside the quote, as every other list pasted
there is (task 1.15 lists that landing), where it threw.

- [x] The Playwright case passes in Chromium, Firefox and WebKit

## Decisions

### 2026-11-28 · A heading that opens a list item is given a shape

**Decision** — A heading directly inside a list item has its shape read with
the item's prefix taken off, so one that opens its item records a shape.
**Rejected** — The refusal stage 1 chose and pinned with a `model` check: a
heading whose line does not start as a heading records `null`, and the emitter
throws on it.
**Why** — The refusal was written as "a spelling the model does not have
rather than one it could guess at". For this shape nothing is guessed: the
marker is the item's, already recorded, and the rest reads as a heading. And
the cost of refusing was not a block left alone but a document that could not
be saved after one keystroke in it.

### 2026-11-28 · A heading in a list item is written from where it sits

**Decision** — The emitter gives a heading its item's marker or continuation
indent on every line, as it gives a paragraph, and the shape holds only what
is past that.
**Rejected** — The first draft: a `marked` flag for a heading behind a marker,
with every other heading's `open` and every underline still holding an
absolute indent. And task 1.16's choice to leave the emitter alone and move
the shape.
**Why** — An indent recorded as bytes goes stale whenever the item moves, and
nothing told the heading. The reader found the draft wrote a setext heading
opening an item as a paragraph after a list switch, and a deep heading as a
code block after an unwrap; a heading further down an item was already
written outside a list switched to numbers, before any of this. Read from the
item at the moment of writing, none of that can happen.
Supersedes: D50

### 2026-11-28 · A heading the item's prefix does not fit stays absolute

**Decision** — A heading in an item whose lines do not start with the item's
marker or indent keeps the shape read from its own column 0, marked
`absolute`, and the emitter adds nothing to it.
**Rejected** — Recording no shape for it, which refuses the document. Reading
it positionally anyway.
**Why** — That is how every heading in an item was written until now, so such
a heading is no worse off, and no oracle heading is one. It is a narrow case:
a line indented short of its item's column, or to the same column in other
bytes, a tab under an item that continues with spaces. Reading the second as
the item's prefix would write the heading back in the item's bytes on any
edit, where it kept its own before.

### 2026-11-28 · A two-line setext heading under an item keeps its indent on every line

**Decision** — Every line of a heading in an item takes the item's indent, so
a setext heading of two lines is written indented on both and on its
underline, pasted or edited.
**Rejected** — Task 1.16's lazy second line.
**Why** — That decision followed from the shape having one indent to record.
Positional, every line gets the item's, and the heading is written the way it
would have been typed.
Supersedes: D51

### 2026-11-28 · What is under a pasted item moves as far as its content did

**Decision** — On adoption an item's continuation indent, the items, fences
and quote chains under it move by the columns its content moved, measured off
its marker before and after.
**Rejected** — The landing column for all of them, as before.
**Why** — A positional heading is written at its item's continuation indent,
so that indent has to be right. For a tab-marked item pasted two columns in
it was not: the marker's tab swallows the move, the content stays at column
4, and the indent was moved to column 8, which also wrote a paragraph there
as a code block. Task 1.16's reader named that fault and left it for a task;
it is fixed here because this change stands on it. With spaces the two
measures are the same number. The measure is taken only where the landing has
no quote chain: behind a `>` the parser places a line's tab stops in a way
this file's column count does not predict, and the second reader found the
measure moved what was under a tab-marked item out of it there, where the
landing column had been right.

### 2026-11-28 · An empty setext heading is written as hashes

**Decision** — A setext heading with no text is written as its level's `#`
run, and content typed in front of a closing run with no space before it gets
one.
**Rejected** — Leaving both, which are wrong at the margin too and older than
this task.
**Why** — Both were unreachable inside an item while such a heading threw,
and reachable there now: Enter at the start of a setext heading wrote `===`
as a paragraph. An underline with nothing over it is not a heading in
markdown, so there is no setext spelling to keep.

### 2026-11-28 · A heading that opens its item writes no indent of its own

**Decision** — The emitter drops the leading whitespace of a positional
heading's `open` when the heading is its item's first child.
**Rejected** — Writing it after the marker, as recorded.
**Why** — After a marker a space is the item's pad. It moves the item's
content column out from under a setext underline written at the item's
indent, and the heading comes back as a paragraph holding `===`; four are a
code block. A parsed heading never has such an indent, the marker having taken
the pad; Enter in a heading indented past its item makes one.

### 2026-11-28 · Two shapes stay refused

**Decision** — `- > # h` and `- - # h` record no shape and the emitter still
throws on an edit to one.
**Rejected** — Keeping the marker, and the `>`, in the heading's `open`.
**Why** — Recorded marker bytes are what the second decision exists to avoid.
A paragraph in either place carries them in its leading affix and has the
faults that follow: task 1.15 lists the first, and the reader measured the
second (`- - pp`, Enter, writes two outer items for one inner list). A loud
refusal is better than joining them.

## What was done

2026-11-28: **done and tested by machine.** The plan as rewritten landed;
CHANGELOG.md has the prose. `modelItemHeadingShape` is new, `modelEmitLeaf`
writes a heading positionally, `modelAdoptBlocks` moves what is under a pasted
item by its content's move, and the emitter has the two spellings of the sixth
decision. The `model` suite gained 85 checks; one of task 1.16's cases changed
with the decision this supersedes, and the check that pinned the refusal now
uses the two shapes still refused. Against the code before, the suite throws
at the first new check. `tests/browser/lists.spec.mjs` gained one case that
passes in Chromium, Firefox and WebKit. `npm test` passes; Playwright is 410
passed with the one recorded Firefox failure. `sw.js` is `v1.108`.

**What no suite reaches**, for the user: a document in daily use. Open a file
with a heading on a bullet's own line, type into the heading, Save As to a
scratch file and diff it against the original; the typed letters should be
the only difference.

Reviewed by: two read-only subagents that had not seen the work, each against the staged diff and briefed with docs/reviewer.md. The first read the first draft and its six findings rewrote the plan. The second read the rewrite: it found every box of the first review to hold against the running code, the six oracle files byte-identical with all 879 inline-bearing leaves re-emitting their own bytes, space-only pastes over 17 landings and 51 shapes byte-identical to the commit before but for the decided setext change, and the five findings of the second Review section. Neither ran Playwright. The fixes after the second reading were checked by the suites and not read again.
