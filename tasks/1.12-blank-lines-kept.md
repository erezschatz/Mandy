# 1.12 — A blank line typed between paragraphs is lost on save

## Context

Reported by the user on 2026-11-19, the day stage 4 merged. They had a song in
an unsaved tab: every line ended with Enter, and every few lines an extra Enter
left a gap between verses. After a close and reopen the text came back with no
gaps. Copying it out lost the gaps as well, and so did saving and reopening.

**Why.** Enter makes a new paragraph, so every line of the song was a paragraph
of its own, and the extra Enter made an *empty* paragraph. Markdown has no way
to write one, so `modelJoinBlocks` in `front/model.js` writes nothing for a
block that emits nothing and takes the separator before it with it (stage 2's
slice 4). That rule exists so that an Enter nobody typed into costs no bytes.
The autosave, Save, Download and Copy markdown all ask that emitter, which is
why the gap vanished from each of them. **An ordinary copy loses it for a
different reason**: Ctrl/Cmd+C goes through `modelInputClipboard` in
`front/model-input.js`, which clones the selected DOM, strips the filler
`<br>` and writes `innerText` as the plain text, and an empty `<p>` adds no
line to that. The file only ever had
one blank line between lines, so every line came back equally spaced.

**What is wrong is not the rule but what the screen promised.** The editor drew
a gap the file could never keep, and said nothing. Of the three ways out put to
the user — keep the gap in the file, stop drawing what will not be kept, or
leave the behaviour and teach Shift+Enter — the user chose the first; the
decision below records it.

**The workaround until this lands** is markdown's own spelling of a verse:
Shift+Enter between the lines of a verse, Enter between verses. That survives
save, reopen and copy today.

### The plan

The promise is **what you see is what is in the file**: an empty paragraph
between two others is written as one more blank line, and a run of extra blank
lines in a file is read back as that many empty paragraphs. Five stages, in
order, each landing on its own.

1.  **Write the gap.** In `modelJoinBlocks`, an empty paragraph that has a
    non-empty block on *both* sides at the top level writes one more line
    between them, so `A`, an empty paragraph and `B` come out as
    `A\n\n\nB`, and two empty paragraphs give two extra lines. One with
    nothing written before it (the start of the document) or after it (the
    end) still costs nothing: a trailing Enter, and the guard paragraph
    `modelEnsureBlock` keeps after a trailing table or rule, must stay free,
    or every document gains a blank line it never had. **The separators need
    one shape**: today an Enter hands the split block's separator on to the
    new empty block, and stage 3's parse will split the same bytes another
    way, so this stage fixes what an empty paragraph between two blocks
    carries as its separator, makes Enter and Backspace produce exactly
    that, and stage 3 parses into it. A check pins that the typed shape and
    the parsed shape write the same bytes. `modelRunLines`, which
    `modelWrapQuote` uses and which copies `modelJoinBlocks`'s rule, changes
    with it, and the comments that state the old rule (at `modelJoinBlocks`,
    in the emitter, and in `modelSettleLists`) are rewritten. Two existing
    `model` suite checks assert the old rule and flip on purpose: *Enter at
    the end of a block leaves the file byte-identical*, on `one\n\ntwo\n`,
    and the split of a quote by Enter, whose empty paragraph lands at the
    top level between two quotes. New checks: the song shape, leading and
    trailing empties costing nothing, the guard paragraph, and every oracle
    file still byte-identical. After this stage Save, the autosave and Copy
    markdown are right, and the screen still loses the gap on reopen.
2.  **Copy the gap.** `modelInputClipboard` writes the plain text from the
    model's markdown, or otherwise makes an empty paragraph between two
    others a blank line in `text/plain`, and the `text/html` keeps an empty
    paragraph a receiving application will show. Which of the two, and
    whether the plain text should be the markdown at all, is decided in this
    stage and recorded.
3.  **Read the gap back.** In `modelParse`, a top-level separator *between
    two blocks* holding more than one blank line becomes the shape stage 1
    fixed: one empty paragraph block per extra line, each with the parser's
    own tokens from a template, the way a paragraph made by Enter gets them.
    **Not the last block's separator, and not the prefix**: blank lines at
    the end or the start of a file have no paragraph after or before them
    and stay bytes, or the trailing-blank-lines round-trip check loses them.
    This changes the invariant that nothing the parser produces emits empty,
    so the bytes must still tile: the empty block's `source` is `""`, and an
    untouched file still comes back byte for byte. The suite's existing edge
    round-trips already hold this shape (*two blank lines between
    paragraphs*); no oracle file does, so `tests/fixtures/torture.md` gains a
    passage that does. Three things in the suite meet empty blocks for the
    first time: the check that the blocks rendered and concatenated are
    `md.render` of the file, which must exempt an empty paragraph by name,
    since markdown-it never renders one; the list wrap, switch and unwrap
    sweep, which visits every paragraph outside an item; and
    `modelSettleLists`, whose parser side will now see parsed empty
    paragraphs. **This changes what existing files look like**: a
    stray double blank line anywhere in a document now shows as a gap.
    That is the promise kept rather than a side effect, but it is visible.
4.  **Machine and hand runs.** A Playwright spec in three engines types the
    song with Enter and an extra Enter between verses, saves it to a scratch
    file, checks the bytes, reloads the page to come back through the
    autosave, and reopens the file, checking the gaps on screen after each.
    Copy markdown is checked against the same bytes, and a Ctrl/Cmd+C of the
    song against what stage 2 decided. The hand residue is the user's own
    song document in Firefox and a paste of it into another application.
5.  **The rest of the reach**, each decided and written down before it is
    built: blank lines inside a quote or a list item, and what the HTML, PDF
    and Word exports show for an empty paragraph. Decided on 2026-11-20 (the
    four decisions of that date below), and built in three parts, each landing
    on its own:

    a.  **A gap inside a quote.** Inside a quote the blank `>` lines are not in
        the separators, as they are at the top level, but blocks of their own,
        of kind `gap`. So `modelReadGaps` gains a quote half: a run of blank
        `>` lines between two blocks of a quote keeps its first line as the
        ordinary one and makes each further line an empty paragraph after it,
        carrying an Enter's shape (a line end, then that line). The joiner
        writes an empty paragraph between two written blocks of a quote as one
        more `>` line, in the spelling the file used where it has one, and
        counts a blank `>` line already written as the blank line it needs. A
        model function says which empty paragraphs are gaps — at the top level
        or in a quote, with something written on both sides — and the copy
        handler asks it, so a copy keeps a quote's gap too. Checks: the seven
        edits around a gap, in a quote, a nested quote and a quote inside a
        list item, each byte-checked and read back to the shape it shows; an
        untouched file byte for byte, `torture.md` gaining a quoted verse; and
        the copy. `copy-gap.spec.mjs`'s case that a quote's empty paragraph is
        not a gap flips on purpose. A paste or a drop landing in a quote or a
        list item is part of it: a gap landing in a quote takes the quote's
        shape, and one landing in a list item is dropped, since a list holds
        no gaps.
    b.  **The exports.** `modelExportClone` keeps a `<br>` in a gap, so the
        HTML export and the PDF draw it a line tall, and the Word export makes
        it one empty paragraph rather than a paragraph holding a break. Only a
        gap: an empty paragraph the file does not write is not in the exports
        either. `exports.spec.mjs` checks each export.
    c.  **A paste back from Mandy.** The copy marks each gap in its HTML;
        `sanitisePastedHtml` keeps a marked paragraph where it drops an
        unmarked one, and the paste converter turns it into an extra blank
        line, which the parse reads back as a gap. A paste from anywhere else
        is unchanged. A Playwright spec copies a song and pastes it into a
        fresh document.

    D25 dropped the gaps under a Blockquote over a selection because a quote's
    gap was not written; part a removes that reason, so whether Blockquote
    should now keep them is put to the user when part a lands, not changed
    quietly.

### Open questions

These are open, and are written up as open rather than answered by default.

- **Containers.** Decided 2026-11-20: a quote keeps a gap, a list does not
  (the two decisions of that date below).
- **Exports.** Decided 2026-11-20: they show a gap (below).
- **Other viewers.** GitHub and every CommonMark renderer collapse a run of
  blank lines into one, so the gap is kept in the file and shown in Mandy,
  but not shown anywhere else that renders the markdown. That is an accepted
  limit of the choice rather than something this task can fix. The
  Shift+Enter spelling is the portable one.
- **A paste of markdown into a container.** Settled by the container
  decisions: stage 5's part a gives a gap landing in a quote the quote's shape
  and drops one landing in a list item.
- **A paste back into Mandy.** Decided 2026-11-20: a paste keeps a gap a copy
  out of Mandy marked (below), and that is stage 5's part c.

## Decisions

### 2026-11-19 · An empty paragraph is written as a blank line

**Decision** — An empty paragraph between two others is saved as one more
blank line, and extra blank lines in a file are read back as empty
paragraphs, so a gap typed with Enter survives save, reopen and copy.
**Rejected** — Drawing an empty paragraph with no height or with a marker, so
the screen never shows what the file cannot keep; and leaving the behaviour
alone while making Shift+Enter easier to discover.
**Why** — The user chose it on 2026-11-19. It is the only option of the three where the gap the user typed is the
gap they get, and the file still reads correctly as plain text. The cost is
that other markdown renderers collapse the gap, and that existing files with
stray double blank lines will show them.

### 2026-11-19 · A copy keeps the gap as text the reader sees, not as markdown

**Decision** — Ctrl/Cmd+C and Edit → Copy go on writing the plain text a
reader sees, and an empty paragraph between two others at the top level is one
more blank line in it — so a run of plain paragraphs copies as
the file's bytes less the final newline, for an LF file. In the HTML such a paragraph keeps a `<br>`, the spelling Word
and Google Docs give an empty paragraph, so a receiving application draws it.
The same reach as the file's rule, and asked of the model as the file asks
it — a block is written when it emits bytes — so not at the ends of the copy,
not inside a container. The plain text is built by marking each such paragraph
with a private-use character the copy does not already hold and replacing the
marker and the two newlines after it with one newline once `innerText` has been
measured.
**Rejected** — Making the plain text the model's markdown for the selection:
it would put `**` and `#` into every copy of formatted text pasted into a plain
field, which is what Export → Copy markdown is for, and a selection starting
mid-block has no markdown of its own to cut from. And writing the plain text
from a `<br>` in the empty paragraph: measured 2026-11-19, `innerText` gives
`<p>a</p><p><br></p><p>b</p>` five newlines in Blink and Gecko and four in
WebKit, against two for the same paragraphs with no gap, so no engine gives
the one extra line and two of them disagree.
**Why** — A copy is for pasting somewhere else, and plain text that is the
reader's text is what every editor people arrive from writes. The marker makes
the answer the same in all three engines.

### 2026-11-19 · A gap read back from a file holds an Enter's separator

**Decision** — An empty paragraph `modelParse` makes of an extra blank line
carries a line end and then that line as its separator, the shape an Enter's
empty paragraph has, so the top level holds one byte more than the file at
each gap and the joiner writes it back without.
**Rejected** — Holding the blank line alone, which keeps the top level an exact
tiling of the file, and converting it to an Enter's shape on the first edit.
Built first and probed: every edit path that takes a block's separator over —
a split, a removal, an insertion after it — reads it before any touch, so Enter
in the gap wrote one blank line too many and a removal left the block before it
with no blank line under it, and each path would have needed teaching.
**Why** — With an Enter's shape a parsed gap is an empty paragraph made by
Enter in every respect but its `source`, so no edit needs to know where it came
from; nothing reads the top level as a concatenation, only through the joiner,
and a container's children, where a gap never is, still tile it exactly.

### 2026-11-19 · A list beside a gap joins across it

**Decision** — Making a paragraph a list item beside a list of the same kind,
with only gaps between them, joins the two lists and takes the gaps out.
**Rejected** — Refusing the command and keeping the gap; and giving the new
list a different bullet character, which markdown reads as a separate list, so
the gap survives at the cost of mixed bullets.
**Why** — The user chose it on 2026-11-19. Markdown keeps two lists of a kind
apart only with something between them that is not a blank line, so the file
would reopen as one list without the gap whatever the screen drew; joining is
what the command did before a file's gaps were read back.

### 2026-11-19 · A list or a quote over a selection drops the gaps inside it

**Decision** — Bulleted list, Numbered list and Blockquote over a selection
covering gaps take the empty paragraphs between two of the formatted blocks
out of the document, and leave the ones at either edge of the selection where
they are; a selection holding nothing but gaps is refused as before.
**Rejected** — Refusing the command, with a notice saying the gap is why.
**Why** — The user chose it on 2026-11-19. A gap cannot be a list item, and
one inside a list or a quote is not written to the file, so formatting around
it would draw what the file cannot keep; until stage 3 the same selection
formatted, because the file's gap was not a block to be in the way.

### 2026-11-20 · A gap inside a quote is kept

**Decision** — An empty paragraph between two blocks of a quote is saved as one
more `>` line, and a run of extra `>` lines in a file is read back as that many
empty paragraphs, as at the top level.
**Rejected** — Leaving a quote's gap drawn and not saved, recorded as a limit.
**Why** — The user chose it on 2026-11-20. It is the promise D20 made, kept one
level in; and unlike a list, a quote is where a verse is quoted.

### 2026-11-21 · Blockquote keeps the gaps inside a selection

Supersedes: D25

**Decision** — Blockquote over a selection keeps the gaps between the blocks it
wraps or unwraps, and leaves the ones at the selection's edges out of it. The
two lists go on dropping the gaps between, as D25 decided for them.
**Rejected** — Dropping them, as D25 did for all three.
**Why** — The user chose it on 2026-11-21. D25 dropped a quote's gaps because
one inside a quote was not written; since a quote's gap is kept (the decision
above), that reason is gone for a quote and stands for a list.

### 2026-11-21 · A split drops a line break at its cut, but not one opening the second half

**Decision** — Enter drops a soft break at the cut from either half, and a hard
break from the end of the first half, and keeps a hard break that opens the
second half.
**Rejected** — Keeping every break at the cut, as before; and dropping every
one, hard breaks opening the second half included.
**Why** — A paragraph cannot end in a break anyone sees: kept, the half ending
in one writes an empty last line, which is a blank line in the file and reopens
as a gap the screen never showed. A soft break opening a paragraph is nothing
either. A hard break opening one is a blank line the reader sees, and a
paragraph may open with one, so dropping it would delete what is on screen.

### 2026-11-21 · Word writes a quote of paragraphs as one paragraph each

**Decision** — The Word export writes a quote as one Word paragraph per child,
each with the quote's indent and border, a gap among them as an empty one and a
nested quote the same way one indent further in; a child that is not a
paragraph — a heading, code, a list — is a paragraph of its text, as the whole
quote used to be.
**Rejected** — Keeping a quote as one Word paragraph and drawing its gap as a
line break inside it.
**Why** — A quote drawn as one paragraph runs its paragraphs together, which
was already wrong before a gap was kept, and a break inside it is two lines
tall where a gap at the top level is one; one Word paragraph per child gives
both the same spacing as the rest of the document.

### 2026-11-21 · A pasted gap is marked with a NUL on its way through Turndown

**Decision** — The `mandyGap` Turndown rule writes a marked gap as a line
holding `\u0000G`, which `htmlFragmentToMarkdown` then removes, leaving the
extra blank line.
**Rejected** — A private-use character such as U+E000, chosen to be absent from
the fragment; and a bare blank line.
**Why** — Measured 2026-11-21: Turndown drops U+E000 from a rule's output, so the
mark vanished before it could be removed, and it collapses blank lines between
blocks to one, so a bare blank line would be lost the same way. A NUL survives
Turndown, as the table rules' marks already rely on, and parsed HTML cannot hold
one, so it can only ever be the mark.

### 2026-11-20 · A list holds no gap

**Decision** — A list item holds no gap: Enter in one starts a new item as
before, an extra blank line inside an item reads as nothing, and a gap pasted
or dropped into an item is dropped.
**Rejected** — Showing and saving an extra blank line inside an item.
**Why** — The user chose it on 2026-11-20. A gap cannot be typed in an item,
since Enter there starts a new one, and an extra blank line in a list means
nothing to any other markdown reader, so it would be a gap only Mandy sees.

### 2026-11-20 · The exports show a gap

**Decision** — The HTML, PDF and Word exports draw a gap as a blank line,
wherever the file writes one; an empty paragraph the file does not write is
not drawn.
**Rejected** — Drawing the document as any markdown viewer would, with no gap.
**Why** — The user chose it on 2026-11-20. An export is the document as Mandy
shows it, and a song exported to PDF without its verse gaps is the bug this
task began with, one step further on.

### 2026-11-20 · A paste keeps the gaps copied out of Mandy

**Decision** — A paste keeps a gap that a copy out of Mandy marked as one, and
goes on dropping the empty paragraphs any other application leaves.
**Rejected** — Keeping every empty paragraph a paste brings, Word's and Google
Docs' blank lines included; and keeping none, with Paste markdown the way to
bring gaps in.
**Why** — The user chose it on 2026-11-20. A copy and a paste within Mandy
should give back what was copied, while the blank lines another application
puts in its HTML are the ghost lines `sanitisePastedHtml` exists to remove.

### 2026-11-20 · Only a block that renders bare keeps its edge whitespace

**Decision** — The rendering trim keeps a block's own edge whitespace only for
a block whose opening token is hidden, a tight item's paragraph, and trims
every other rendering whole. A block with an inline tree and no opening token
to ask is treated as bare too, keeping the older and more careful answer; none
of the oracle's 1,093 inline-bearing leaves takes that branch.
**Rejected** — Leaving the trim as it was and removing the whitespace text
nodes beside a block's element after it is built; and asking whether the
rendering ends in a closing tag.
**Why** — The first cleans up after a wrong answer rather than giving the right
one, and would have to tell a paragraph's own text from markdown-it's line end
again. The second cannot tell `a <strong>b</strong> `, a bare paragraph whose
trailing space is content, from `<p>a </p>`. Whether the block has a tag of its
own is the one fact that decides it, and the token says so.
